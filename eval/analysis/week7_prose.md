# 7주차: 보고서 서술의 사실 정확성

## 질문

3주차 이후 트리아지 평가는 60/60으로 포화됐다. 그런데 이 평가는 보고서의 **구조화된 필드**(취약점 ID, 업그레이드
버전, 순위)만 채점한다. 사람이 실제로 읽는 `summary` / `reason` / `notes`는 아무도 검사하지 않았다.
**구조화된 필드가 만점인 보고서의 서술은 맞나?**

## 먼저 무료로 확인

새 평가를 만들기 전에, 이미 있는 v4 실행 기록 60개(Haiku 5.5, 20 케이스 × 3회)를 읽고 코드로 대조했다.
10개를 직접 읽어 보니 조치 설명과 한계 고지(전이 의존성 미검사, "OSV 결과 없음 ≠ 안전")는 양호했지만,
**요약문의 개수가 자주 틀렸다**: "의존성 44개"(실제 43), "12개 패키지에서 20건"(실제 8개, 19건).
그래서 LLM 채점(설명 품질) 대신, 코드로 잴 수 있는 서술의 사실 정확성을 먼저 재기로 했다.

## 채점 (코드, 비용 0)

`eval/prose_grade.py`. 정답 파일이 아니라 **그 실행에서 받은 도구 결과**와 대조한다.

| 지표 | 내용 |
|---|---|
| prose_ok (대표) | 아래가 모두 통과 |
| counts_ok | 요약의 "N개 / N건"이 사실과 맞다. 숫자가 무엇을 센 것인지(취약점 / 취약 패키지 / 의존성) 주변 낱말로 추정해 그 대상의 값과 비교. 근사 표현("약 / 여 / 이상")은 ±10%(최소 ±2) 허용 |
| ids_grounded | 서술의 CVE / GHSA / PYSEC ID가 모두 도구 결과에 있다 |
| kev_consistent | "KEV 항목 없음"류 주장이 도구 결과와 모순되지 않는다 |
| top1_named | 요약이 정책 1순위 취약점(ID 또는 패키지)을 언급한다 |
| korean_only | 가나·한자가 섞이지 않았다 |

`eval/prose_eval.py`는 트리아지 평가의 실행 기록을 그대로 다시 채점한다. 같은 실행을 두 평가가 각자 보므로
새 API 호출이 없다.

## 결과 (기준선: v4 실행 60개)

| 지표 | 통과 | 95% CI |
|---|---|---|
| **prose_ok** | **38/60 (63%)** | 51–74% |
| counts_ok | 39/60 (65%) | 52–76% |
| ids_grounded | 60/60 | 94–100% |
| kev_consistent | 60/60 | 94–100% |
| top1_named | 59/60 | 91–100% |
| korean_only | 59/60 ("ランサム웨어") | 91–100% |

같은 60개 실행이 구조화된 필드 채점에서는 60/60이다. **보고서의 데이터는 맞는데 그 데이터를 요약한 문장이 틀린다.**
개수 오류는 취약 패키지가 여럿이라 직접 더해야 하는 케이스에 몰린다(java-goof-core·nodegoat·pygoat 3/3).
취약 패키지가 하나뿐인 케이스는 취약점이 29개여도(django-nv) 틀리지 않았다. 모델이 손으로 합산하다 틀린다.

## 채점기 검증: 사람 라벨 대신 변이 테스트와 플래그 전수 확인

이 채점기의 정답(실제 개수)은 도구 결과에 이미 있다. 채점기가 틀리는 방식은 "틀린 숫자를 놓침"과 "맞는 숫자를
틀렸다고 함" 둘뿐이므로 사람 라벨 없이 각각 잴 수 있다.

**놓침 — 변이 테스트** (`eval/prose/mutation_test.py`): 채점기가 맞다고 본 요약문 39개의 개수 표현 81개를
하나씩 바꿔 오류를 만들었다. 원래 숫자가 맞았다면 바꾼 숫자는 반드시 틀린 것이다.

| 변이 | 처음 채점기 | 대상 추정 추가 후 |
|---|---|---|
| 사실표에 없는 값 (n±1, 2n+3) | 179/179 (100%) | 179/179 (100%) |
| 사실표의 다른 항목 값 (대상을 엉뚱하게: "취약점 4건"인데 4는 취약 패키지 수) | **0/266 (0%)** | **146/266 (54.9%)** |
| 범위 밖 근사 ("약 m") | 45/81 (56%) | 59/81 (72.8%) |
| 맞는 숫자에 "약"만 붙임 (통과해야 함) | 81/81 | 81/81 |

처음 채점기는 숫자가 사실표 "어딘가"에 있으면 통과시켜서, 대상을 잘못 쓴 오류를 하나도 못 잡았다. 변이 테스트가
없었다면 몰랐을 결함이다. 숫자 주변 낱말로 대상을 추정하게 고쳐 절반 이상 잡게 됐다.

**오탐 — 플래그 전수 확인**: 실제 보고서에서 채점기가 틀렸다고 한 21개를 하나씩 사실과 대조했다. **21개 모두 실제
오류**였다(보고서 단위 정밀도 21/21). 숫자 단위로는 1건이 오탐이었다("1,479개"를 479로 읽음, 고침).

## 채점기를 만들며 잡은 채점기 버그

| 버그 | 어떻게 발견 | 영향 |
|---|---|---|
| `\b`로 ID 경계를 잡아 "CVE-2021-44228은"처럼 한글 조사가 붙은 ID를 못 찾음 (한글도 단어 문자) | 단위 테스트 | 지어낸 ID를 놓칠 수 있었다 |
| 파서 메모의 버전 문자열(2.6.3)의 숫자까지 허용값에 넣음 | 라벨링 파일을 만들다 사실표에서 발견 | 작은 숫자 오류가 통과 |
| "취약점 총 37건 중"의 "중"을 보고 패키지 수로 분류 | 대상 추정 추가 후 새로 생긴 플래그 확인 | 맞는 요약을 틀렸다고 함 |
| 천 단위 쉼표 "1,479"를 479로 읽음 | 플래그 전수 확인 | 오탐 |

## 한계

- 대상을 엉뚱하게 쓴 오류의 45%는 아직 놓친다. 대부분은 같은 종류 안의 혼동이고("직접 의존성 13개"를 취약 패키지 수
  4로 바꾼 경우처럼 둘 다 패키지 수), 나머지는 대상을 추정할 낱말이 없는 경우다("스타터 2개는 확인하지 못했다")
- 개수 검사는 `summary`만 본다. `reason` / `notes`의 숫자는 아직 보지 않는다
- 변이 테스트는 내가 상상한 오류 유형만 검사한다. 사람 라벨은 받지 않았고, 라벨링 파일(`eval/prose/labeling.md`)은
  설명 품질을 LLM으로 채점할 때(사람 판단이 정말 필요한 기준) 쓰려고 남겨 두었다
- 표본은 20 케이스 × 3회다. 개선을 비교할 때 노이즈 폭은 약 ±13%p

## 개선: v5 — 개수도 코드가 센다

원인은 모델이 여러 패키지의 개수를 손으로 더하다 틀리는 것이었다. 3주차에 정렬과 버전 계산을 도구로 옮긴 것과 같은
처방을 했다. 바꾼 것은 하나다 (`.claude/hillclimb/triage/v5/change.md`).

- `check_packages`(tool hints)가 `counts`(검사한 패키지, 취약 패키지, 취약점 없는 패키지, 취약점 합계, 고유 취약점,
  KEV)와 패키지별 `vulnerability_count`를 돌려준다. 같은 취약점이 두 패키지에 걸리면 합계와 고유 개수가 달라서
  (benchmark-java: 28건, 고유 27건) 둘 다 준다
- 사용자 메시지에 입력 쪽 개수(검사 대상, 검사하지 못한 항목)를 넣는다. 검사하지 못한 항목 수는 도구가 모른다
- 프롬프트와 MCP 도구 설명: 서술의 모든 숫자는 이 필드에서 옮겨 쓰고 손으로 세지 말 것
- 채점기는 여전히 `results`에서 직접 센다. `counts`를 읽으면 도구의 개수 버그를 못 잡기 때문이다

진행: 무료 검사(CI 전체, 20 케이스 모두 도구 개수 = 채점기 사실) → 가장 많이 틀린 3 케이스로 파일럿($0.03) →
전체 60회. 파일럿 비용은 v4의 1.5배로 나왔지만 출력 토큰은 늘지 않았고, v4의 2~3회차는 캐시를 재사용해 싸졌는데
파일럿은 1회씩만 돌아 캐시가 없었던 탓이다. 예상 $0.25–0.31을 알리고 상한을 올려 돌렸고, 실제 비용은 $0.205였다.

### 결과 (같은 20 케이스 × 3회, 같은 채점기 버전)

| 지표 | v4 | v5 |
|---|---|---|
| **서술 모두 정확 (prose_ok)** | **38/60 (63%, CI 51–74%)** | **59/60 (98%, CI 91–100%)** |
| 개수 정확 (counts_ok) | 39/60 | 60/60 |
| 1순위 언급 | 59/60 | 59/60 |
| 한국어만 | 59/60 | 60/60 |
| 구조화 필드 통과 (기존 평가) | 60/60 | 60/60 |
| 실행당 비용 | $0.0034 | $0.0034 |
| 지연 중앙값 / p90 | 13.2s / 34.0s | 12.1s / 32.1s |
| 출력 토큰 중앙값 | 3,278 | 2,823 |
| 요약당 개수 표현 수 (생략으로 점수를 얻지 않았나) | 2.7 | 4.6 |

케이스별로 짝지어 보면 10개 케이스가 좋아졌고 나빠진 케이스는 없다. v4에서 3회 모두 틀렸던 java-goof-core,
nodegoat, pygoat는 3회 모두 맞았다. 요약은 숫자를 덜 쓴 게 아니라 더 많이 쓰면서 맞았다.

### 이 수치를 믿을 수 있나

- **채점기를 결과를 본 뒤 고쳤다.** v5 결과를 보며 채점기 오탐 4종을 찾았다(아래 표). 모두 맞는 서술을 틀렸다고 한
  경우라 고쳤고, 고칠 때마다 v4 기준선을 같은 버전으로 다시 채점했다. **기준선은 세 번의 수정 내내 38/60 그대로**였다.
  고치기 전 채점기로도 v5는 55/60(92%, CI 82–96%)으로 신뢰구간이 기준선과 겹치지 않는다
- **만점이 채점기의 맹점 아닌가.** 대상을 엉뚱하게 쓴 오류는 아직 45%를 놓친다. 그래서 전에 틀렸던 케이스의 v5 요약
  10개를 사실표와 직접 대조했다. 숫자 모두 맞았다
- 변이 테스트 결과는 수정 전후 그대로다(사실표에 없는 값 100%, 대상 오류 55%, 맞는 근사 오탐 0)

### v5 결과를 보며 찾은 채점기 오탐

| 서술 (모두 맞는 문장) | 채점기가 본 것 | 수정 |
|---|---|---|
| "나머지 9개 패키지에서는 알려진 취약점이 없었다" | "N개 패키지에서" → 취약 패키지 수 | "나머지"가 앞에 있으면 일반 패키지 수 |
| "Log4j 2.7(9개 취약점, KEV 2개)" | 패키지별 KEV 개수를 모름 | 사실에 패키지별 KEV 개수 추가 |
| "검사하지 못한 항목은 95건" | "건" → 취약점 수 | "검사하지 못한 / 검사 불가" 뒤의 숫자는 항목 수 |
| "가장 시급한 대상은 Apache Struts2 2.3.20" | `struts2-core`라는 정확한 이름만 인정 | `-core` / `-api` 같은 접미사를 뗀 이름도 인정 |

v5가 숫자를 더 많이, 더 다양한 표현으로 쓰면서 채점기가 처음 보는 문장이 늘었다. 개선이 평가의 빈틈을 드러낸 셈이다.

### 남은 실패 1건과 다음

java-goof-core 1회: 보고서 순위(정책: KEV → EPSS)의 1위는 spring-context인데, 요약은 hsqldb의 CRITICAL 원격 코드
실행을 "가장 시급"하다고 썼다. v4에도 같은 실패가 있었다. 계산 실수가 아니라 **심각도와 정책 순위가 충돌할 때 무엇을
앞세울지**의 문제라 스펙 결정이 먼저다(정책을 바꿀지, 요약에서 둘 다 말하게 할지).
