# 4주차 (1): CWE 검색과 검색 평가

## 질문

CVE 설명만 보고 그 취약점의 유형(CWE)을 찾아 설명하고 완화책을 제시하려면, CWE 지식베이스에서 맞는 항목을
찾아와야 한다. **어떤 검색 방식이 가장 잘 찾나?** 그리고 평가 숫자를 믿어도 되나?

## 데이터

- 지식베이스: MITRE CWE 5.0 (2026-10-28). 취약점 유형 956개 + 분류(Grouping) 396개 = 1,352개 (Deprecated 제외)
- 질의: 1주차에 캐시한 NVD 레코드 438개의 영어 설명
- 정답: 같은 레코드에 NVD 또는 CNA가 붙인 CWE 라벨. 새로 라벨링하지 않았다 (비용 0)
- LLM 호출 없음. 임베딩은 서버에 이미 받아 둔 모델을 CPU 8스레드로 계산 (공용 서버 GPU 사용 안 함)

## 발견

1. **범용 문장 임베딩은 BM25보다 나빴다.** 두 모델 모두 일반 문장 유사도로 학습된 것이라, 짧은 CVE 설명으로
   긴 CWE 정의를 찾는 비대칭 검색에 맞지 않는다. "임베딩이면 더 잘 찾겠지"는 측정해 보기 전까지는 가정이다.
2. **CWE의 '관찰 사례'를 색인하면 hit@5가 0.33 → 0.47로 오른다.**
   - 처음에는 누수를 의심했다. 관찰 사례에는 실제 CVE 설명이 실려 있어서, 질의 CVE가 그대로 들어 있으면 정답을 베끼는 셈이기 때문이다.
   - 그래서 자기 CVE가 실려 있는 질의(5개)를 빼고 다시 쟀다. 상승폭이 그대로였고, 신뢰구간도 겹치지 않았다.
   - 결론: 이 상승은 관찰 사례가 CVE 설명과 **같은 문체**라서 생기는 정당한 효과다.
3. 관찰 사례를 넣은 BM25에 임베딩을 섞으면 오히려 떨어진다 (0.47 → 0.41). 약한 순위를 섞으면 강한 순위가 희석된다.
4. **채택: BM25 + 관찰 사례** (security-kb 서버 기본값). 가장 정확하고 가장 빠르며, torch를 올릴 필요도 없다.

## 숫자를 읽을 때 주의할 점

- 라벨에 잡음이 많다. 가장 흔한 정답이 CWE-400(자원 소모), CWE-20(입력 검증), CWE-770 같은 넓은 항목이고,
  같은 버그에 사람마다 다른 CWE를 붙인다. hit@1이 낮은 이유의 상당 부분은 '틀린 검색'이 아니라 '여러 정답 중
  하나만 라벨로 붙은 것'이다. 그래서 hit@5/hit@10을 주 지표로 본다.
- 질의가 2주차 케이스에서 나온 CVE라 웹 프레임워크·라이브러리 취약점에 치우쳐 있다.
