# 8주차: CWE 지식베이스를 에이전트에 연결하면 나아지나?

## 질문

4주차에 CWE 검색기(BM25 + 관찰 사례, hit@5 0.475)를 만들어 security-kb MCP 서버로 띄웠지만, 트리아지
에이전트는 그 서버를 쓰지 않았다. 보고서에 취약점 유형(CWE)과 "업그레이드 전까지 무엇을 하라"는 완화책을
넣으려면 지식베이스가 필요해 보인다. **실제로 연결하면 CWE와 완화책이 더 정확해지나?**

## 먼저 공짜로 확인한 것 (LLM 호출 없음)

`eval/cwe/retrieval_check.py` (결과: `eval/cwe/retrieval_check.json`)

1. **라벨이 이미 있다.** 평가 케이스의 고유 취약점 466건 중 456건(98%)에 GHSA나 NVD가 CWE를 붙여 두었다.
   둘 다 붙인 432건 중 359건은 같은 집합, 68건은 일부만 겹치고, 5건은 완전히 다르다. 그래서 정답은
   GHSA ∪ NVD로 하고 둘 중 하나라도 맞으면 정답으로 본다.
2. **에이전트가 보는 텍스트로는 검색이 약하다.** check_packages는 한 줄짜리 OSV 요약만 준다. 이것으로
   검색하면 정답 CWE가 1위인 경우 27%, 상위 5개 안 45%다 (NVD 설명으로는 23% / 49%).
   4주차 수치(0.475)와 비슷하지만, 질의가 더 짧은데도 hit@1은 오히려 조금 높다.
3. 그래서 "라벨을 숨기고 검색 후보에서 고르게" 하면, 후보 밖을 고르지 않는 한 정확도 상한이 약 45%다.

이 결과로 실험을 셋으로 나눴다. 검색만 붙여 보면 "검색을 붙였더니 몇 %"라는 숫자만 나오고,
그게 좋은지 나쁜지 비교할 기준이 없다.

## 실험 설계

세 실험군 모두 v5(Haiku 5.5 + 검증 루프 + 결정적 계산 도구)와 같고, 보고서에 두 필드를 더했다:
취약점마다 `cwe`, 패키지마다 `workaround` (업그레이드로 다 못 고치는 패키지만, 한국어, 근거 CWE를 괄호로 인용).
다른 점은 CWE 정보를 어디서 얻느냐 하나다.

| 실험군 | CWE 정보 | 붙는 MCP 도구 |
|---|---|---|
| v6a 기억만 | 없음. get_vulnerability의 CWE 필드도 숨김 | vuln-data만 |
| v6b 라벨 전달 | check_packages가 GHSA/NVD 라벨과 이름을 붙여 줌 | + security-kb: get_weakness, search_weaknesses(라벨 없을 때만) |
| v6c 검색 | 라벨 숨김. 검색 후보 중에서 골라야 함 | + security-kb: search_weaknesses_many(묶음 검색), get_weakness |

- 에이전트가 두 MCP 서버(vuln-data, security-kb)에 동시에 붙는다. 도구 이름으로 어느 서버에 보낼지 정한다.
- v6c에서 취약점마다 검색을 한 번씩 부르면 pygoat는 190번이라 턴 제한(8)에 걸린다. 그래서 질의를 묶어
  한 번에 보내는 `search_weaknesses_many`를 security-kb에 더했다 (후보마다 id와 이름만, 요약은 뺌).
- 케이스: 취약점이 있는 16개 × 1회 × 3실험군. 취약점 단위 지표는 실험군마다 545개(케이스·취약점 쌍)라
  1회로도 표본이 크다. 실행 단위 지표(구조화 pass, 서술 prose_ok)는 16개라 회귀 확인용으로만 본다.

## 채점 (전부 코드, 비용 0)

`eval/cwe_grade.py`. 7주차에 사용자와 정한 원칙대로 LLM 채점기 없이 시작했다. 사람 라벨링 파일(7주차)은
요약 서술용이라 CWE·완화책 채점에는 맞지 않는다.

| 지표 | 정의 |
|---|---|
| CWE 정답률 | 보고한 cwe가 정답 라벨 중 하나. 보고서에서 빠진 취약점은 오답, 라벨이 카탈로그에 없는 취약점은 제외 |
| 채움 / 카탈로그에 있음 | null이 아닌 비율 / 채운 값이 실제 CWE 번호인 비율 (지어낸 번호 탐지) |
| 도구 근거 | 채운 cwe가 그 실행의 도구 결과 어딘가에 나왔나 (기억에서 꺼낸 것과 구분) |
| 완화책 작성 | 업그레이드 하나로 모든 취약점을 벗어날 수 없는 패키지 7개(케이스 5개)에 workaround를 썼나 |
| 완화책 CWE 맞음 | workaround가 인용한 CWE 중 하나가 그 패키지 취약점의 정답 라벨에 있나 |
| 완화책 KB 근거 | 인용한 CWE 중 하나를 그 실행에서 get_weakness로 조회했나 |

같은 실행을 기존 채점기(구조화 필드 `grade.py`, 서술 `prose_grade.py`)로도 다시 채점해, CWE를 더하느라
기존 품질이 떨어지지 않았는지 본다.

채점기 자체 점검 (CI에 추가): 스냅샷에서 라벨을 다시 만들면 커밋된 것과 같고, 정답 라벨을 그대로 쓴 보고서는
545/545·완화책 7/7, CWE를 비운 보고서는 0/545.

서술 채점기 변경 두 가지 (검색 결과도 "results" 필드를 가져서 check_packages 결과로 잘못 읽을 수 있었고,
"XSS(CWE-79) 7건" 같은 CWE별 개수를 허용해야 했다): 바꾼 뒤 v4 38/60, v5 59/60 그대로.

### 검색 실험군이 왜 낮은가: 검색 탓인가, 선택 탓인가

`search_weaknesses_many` 호출 기록에서 취약점마다 받은 후보 5개를 꺼내 나눴다 (검색한 취약점 544개).

| | 개수 | 비율 |
|---|---|---|
| 후보 5개 안에 정답이 있었음 (검색 재현율) | 232 | 43% |
| 검색기 1위가 정답 (검색기만 썼다면) | 139 | 26% |
| 에이전트 정답 | 240 | 44% |
| ㄴ 후보 중에서 골라 맞음 | 214 | 정답이 후보에 있던 232개 중 92% |
| ㄴ 후보 밖에서 (기억으로) 맞음 | 26 | |
| 오답: 정답이 후보에 있었는데 다른 것을 고름 | 16 | |
| 오답: 후보에 정답이 없었음 | 288 | 오답의 95% |
| 비움 (맞는 후보가 없다고 판단) | 147 | 27% |

- **에이전트의 선택은 좋다.** 검색기 1위(26%)에서 44%로 올렸고, 후보에 정답이 있을 때는 92%를 골라냈다.
  4주차에 다음 후보로 적어 둔 "LLM 재순위화"의 효과가 여기서 측정됐다.
- **병목은 검색 재현율(43%)이다.** 오답의 95%는 후보에 정답이 아예 없었다. 사전 점검(공짜)에서 잰 상한 45%와
  거의 같고, 파일럿 2케이스(후보 안 정답 63%)는 평균보다 쉬운 케이스였다.
- **이 실험군은 "후보 안에서 고르기"를 잰 것이다.** 프롬프트가 "후보 중 맞는 것을 고르고, 맞는 게 없으면 null"이라고
  지시했으므로, 비움 147개와 후보 밖 정답이 26개뿐인 것은 대부분 지시를 따른 결과다. "검색 결과가 기억을 덮어썼다"고
  말할 수는 없다. 비교는 후보로 제한한 선택(44%)과 제한 없는 기억(64%)이다.
  후보를 참고로만 주고 기억도 쓰게 하는 실험군(검색 + 기억)은 돌리지 않았다.

### 완화책을 읽어 보면

"KB 근거"는 조회하고 인용했다는 뜻일 뿐이라, 라벨 전달 실험군의 완화책 7개를 조회한 MITRE 완화책과 나란히 읽었다.
7개 모두 조회한 내용을 한국어로 옮긴 것이었다. 예: CWE-502 → HMAC 서명으로 변조를 확인한 뒤에만 역직렬화,
CWE-434 → 사용자 파일명 대신 새 고유 파일명, CWE-674 → 재귀 깊이 검사와 스택 크기. 일부는 "1.78 이상으로 올려 3건을
먼저 해소" 같은 부분 업그레이드 안내를 덧붙였는데, 이 버전·건수는 채점하지 않았다.

### 기억만 쓰면

- 64%이고, 지어낸 CWE 번호는 0개였다 (채운 값이 전부 카탈로그에 있음). 눈으로 본 오답 몇 개는 그럴듯한 이웃이었다:
  CWE-178(대소문자 처리) vs 정답 CWE-20(입력 검증), CWE-502(역직렬화) vs CWE-470(안전하지 않은 리플렉션).
  오답 전체가 그런지, 상하위 관계로 부분 점수를 주면 얼마인지는 재지 않았다.
- 완화책 7개 모두 맞는 CWE를 인용했지만 근거가 없다. 지식베이스를 조회하지 않았으니 MITRE 완화책과 맞는지
  확인할 방법이 없다 (KB 근거 0/7).

### 비용과 기존 품질

- 기존 구조화 필드(16/16)와 서술 사실(16/16)은 세 실험군 모두 떨어지지 않았다.
- CWE와 완화책을 넣는 비용은 실행당 v5 대비 +$0.003 (라벨 전달 $0.0041 → $0.0072, 출력 토큰 5.6천 → 8.2천).
  라벨 전달과 기억의 지연 차이는 작다 (중앙값 20.4s vs 23.5s, 출력 토큰은 거의 같음).
- 검색은 가장 비싸고(+$0.0056) 가장 느렸다 (38.7s): 질의 545개를 출력 토큰으로 써야 하고 후보 목록이 입력으로 돌아온다.

## 결론

1. **CWE는 검색하지 말고 이미 있는 라벨을 쓴다.** 라벨 전달이 정확도(100%), 근거(완화책 7/7이 지식베이스 조회),
   비용·속도 모두 가장 좋다. 지식베이스는 "찾기"가 아니라 "id로 조회해 완화책 근거 대기"에 쓴다.
2. **검색 후보 안에서 고르게 하면 기억보다 낮았다 (64% → 44%).** 에이전트의 후보 선택은 잘 동작했지만(검색기 1위 26% →
   44%), 검색 재현율 43%가 상한이 된다. 4주차에 "임베딩이면 낫겠지"를 재 보고 뒤집었듯, "RAG를 붙이면 낫겠지"도
   기준선(기억만)과 비교하기 전에는 가정이었다. 다만 후보를 참고로만 주는 방식은 재지 않았다.
3. 검색의 자리는 라벨이 없는 2%의 대안이다. 라벨 전달 실험군에서도 그 용도로만 열어 두었다.

## 한계

- 1회 실행이다. 취약점 단위 표본(545)은 크지만 같은 케이스 안의 취약점끼리 상관이 있어, 신뢰구간은 실제보다 좁다.
  그래도 기억과 검색의 차이(20%p)는 케이스 16개 모두에서 같은 방향이었다.
- 정답 라벨 자체에 잡음이 있다 (GHSA와 NVD가 73건에서 다르게 붙임). 라벨 전달 100%는 "라벨을 정확히 옮겼다"는
  뜻이지 "라벨이 맞다"는 뜻이 아니다.
- **돌리지 않은 실험군:** 검색 후보를 참고로만 주고 기억도 허용하는 방식. 검색 실험군의 44%는 "후보 안에서 고르라"는
  지시를 포함한 숫자라, 검색을 다르게 붙이면 기억(64%)보다 나을 수도 있다.
- 완화책 내용은 코드로 채점하지 않았다 (인용한 CWE와 조회 여부만). 라벨 전달 7개는 사람이 읽어 확인했다. 규모가 커지면
  LLM 채점기를 만들고, 다른 CWE의 완화책으로 바꿔 넣는 변이 테스트로 검증한다.
- 검색 질의는 OSV 한 줄 요약이었다. NVD 설명(사전 점검 hit@5 0.49)이나 검색용 임베딩으로 재현율을 올리면
  결과가 달라질 수 있다.

## 평가가 잡은 것 (이번 주)

- **채점기 정의 오류:** 파일럿에서 세 실험군 모두 spring-context 3.2.6에 완화책을 쓰지 않았다. 보니 에이전트가 맞았다.
  CVE-2024-38820은 5.3.x 줄에 수정이 없을 뿐이고(last_affected) 6.1.20으로 올리면 벗어난다. "수정 없는 취약점이 있는
  패키지"가 아니라 "단일 안전 업그레이드가 없는 패키지"가 맞는 정의였다 (14개 → 7개). 하네스는 그대로라 파일럿 실행을
  본실행에 재사용했다.
- **서술 채점기 오탐 2종** (맞는 문장을 틀렸다고 함): "28개 패키지에서는 OSV가 알려진 취약점을 반환하지 않았습니다"를
  취약 패키지 수로, "range 지정 의존성 95건은"을 취약점 수로 읽었다. 고친 뒤 v4 38/60, v5 59/60, 변이 테스트 검출률
  (100% / 55% / 72.8% / 100%) 모두 그대로.
- **검색 결과가 check_packages 결과로 읽힐 뻔했다.** 둘 다 `results` 필드가 있어서, 서술 채점기가 검색 결과를 사실표로
  쓸 수 있었다. 실행 전에 테스트로 막았다 (`as_of`가 있는 것만).
